## 1. Open bugs, in priority order

### 1.1 Retake lock copy is written for the wrong product

`src/features/assessment/components/public/assessment-runner.tsx` around line 1370 hardcodes:

> Meaningful emotional and behavioural change requires time and consistent implementation.
> Your next reassessment will be available on {date}.

That is coaching language. It now renders on a B2B lead-qualification funnel that paid
traffic lands on, which reads as the wrong product entirely. It is a literal string, not
database content, so there is no data leak; it is a brand defect.

Fix: neutral wording, or wording the assessment owns. Check whether other hardcoded
respondent-facing copy in that file has the same problem.

### 1.2 Sign-up session mismatch

A prospect completing the platform signup funnel is redirected to
`/sign-up?email=...&name=...`. If the browser already holds ANY session, `src/middleware.ts`
(around line 46) bounces them to `/dashboard` using `nextUrl.clone()`, which keeps the query
string. The prospect lands in somebody else's dashboard with no signup and no explanation.

Harmless when testing on your own machine. Not harmless on a shared or kiosk device, or when
a prospect already has an account under a different email.

Fix: when the request carries an `email` parameter that does not match the session's email,
let `/sign-up` keep the request and offer a choice ("You are signed in as X. Continue, or
sign out to create an account for Y."). The middleware redirect currently fires first, so
the exemption has to live there.

### 1.3 Countdown on the signup path

`vslCountdownSeconds` (10 on the junk-leads funnel) covers server scoring before a VSL
destination. On a signup funnel it is ten seconds of nothing before a redirect. Either skip
it when the funnel hands off to signup, or document that owners should set it to 0.

### 1.4 Unexplained, do not guess again

An intermittent save failure in the Assessment Builder: the button hung on "Saving..." and
the page fell through to the error boundary. I diagnosed it as the Server Action 1 MB body
limit, raised the limit to 8 MB, and the user then proved the save had worked before that
commit reached main. **So the cause is unknown.** The raised limit is correct hardening and
fixed nothing. If it recurs, get the `digest` from the browser console (the boundary logs
`[app error boundary]`) and the Railway log. Do not propose a cause without one.

## 3. Decisions that must not be re-litigated

**The SEO content model.** The atomic unit is an ANSWER: one question, one file, two
lengths. `short` is a single sentence (Zod rejects a second one); `body` is the expansion
and needs at least two sections, which is the anti-thin-page floor. Pillars compose a
cluster; `/answers/<slug>` renders one. Only the sentence appears on both surfaces and the
answer page is its canonical home.

**Positioning: Gate, Score, Review, Signal.** The named mechanism, repeated across every
guide. Gate decides who is worth asking, Score decides fit, Review catches what scoring
cannot judge, Signal teaches the ad platform. Stated as a LOOP, because step four feeds step
one. "Software" never attaches to the Assess360 name; the category term survives in the URL,
the title tag and the first sentence of the matching answer, which is where it earns
ranking. No uniqueness claims anywhere: the owner knows the Meta exclusion loop is
unmatched, and it stays internal knowledge rather than published copy.

**Keyword rule.** Pillars own noun queries, answers own question queries. `verify:seo` fails
if a term is primary on two pages.

**No long dashes.** Em and en dashes are banned everywhere, including chat replies, docs and
any generated file. Use a comma when the dash joins a clause, a hyphen when it labels.
**Twenty-six remain deliberately:**
- 10 are DETECTORS and their fixtures: the character classes in `humanizeStatement`
  (`src/lib/ai/prompt.ts`), the two band parsers (`parse-assessment-text.ts`,
  `parse-bands-text.ts`), and the `scripts/verify-ai.ts` tests that exercise them. A regex
  that detects a long dash is the opposite of using one. A blind sweep broke all of these
  once and every automated gate passed while they were broken.
- 16 are in APPLIED Prisma migrations. Prisma checksums those; editing one makes
  `migrate deploy` fail and no deploy would start again, the rollback included.

## 4. The gates, and one hard-won correction

Before every push:

```
npx next typegen && npx tsc --noEmit && npx eslint . && npm run verify:seo
```

🔴 **`npx next lint` is NOT the gate.** It passed with 3 warnings and 0 errors while the
Railway build failed on 7 `no-html-link-for-pages` errors. `npx eslint .` reproduces what
the build does. `next typegen` regenerates `.next/types` without a build, so tsc can check
App Router route signatures it otherwise cannot see.

**A trap worth remembering:** a root-level dynamic segment (`src/app/[slug]/page.tsx`) makes
`no-html-link-for-pages` treat arbitrary paths as pages and fire on `<a>` tags in unrelated
files, including `/api/...` download endpoints that must stay plain anchors. Pillars are
bound to explicit static route folders for this reason, and `verify:seo` asserts every
registry page has one.

## 5. Known limitations, stated rather than discovered later

- The page builder's DRAFT pages are a separate table and are still not exported; only the
  published snapshot travels.
- `aiPromptVersionId` is excluded from export: it is a foreign key to a row that will not
  exist in the target environment.
- The robots.txt platform branch only runs on the production host, so it cannot be observed
  on staging. `verify:seo` asserts it as a pure function instead.
- Staging has its own database. Production assessments do not exist there, so a 404 on
  staging for a production slug is expected, not a regression.
