## 1. What shipped, and why

### The funnel (ads land here, treat with care)

**The countdown is bound to where a run ENDS, not to the step.** `features/assessment/flow/stages.ts`
is a pure function: signup, result pages, payment, destination, in that precedence. Only a
destination redirect gets the anticipation timer; everything else shows a plain spinner,
because the next screen appears as soon as the server answers. No branch in that file names
a funnel type. `npm run verify:flow` pins the order and the clamping.

**No AI statement on a signup funnel.** That run ends at `/sign-up` and never renders a
result, so the LLM call was writing for nobody and costing the respondent eight to ten
seconds between an ad click and a trial. Scoring, metering, the completion event and the
CAPI fan-out are untouched.

**A locked retaker on a signup funnel goes to the account.** The retake lock is keyed on
email in the DATABASE, so incognito does not help; someone who completed a trial funnel
already has an account, and the lock now routes to the signup hand-off rather than a dead
end telling them to come back in fifteen days.

**Finishing an assessment and signing in are SEPARATE EVENTS.** This is a rule, not a fix.
An `email` parameter on `/sign-up` means a funnel just finished, so that page acknowledges
and offers a button; it never redirects on its own. Breaking this teleports a tenant out of
their own test run, and on a shared browser drops a prospect into someone else's workspace.
The middleware exemption exists for the same reason: the edge cannot read a session, so it
lets that one request through and the page compares the two emails.

**One editable line above the opt-in** (`Assessment.qualifiedNote`). After a gate, the
landing copy is suppressed and the reward for qualifying was a bare form headed "Almost
done". This is where the offer goes. One free-text field on purpose: offers change weekly,
and a structured block becomes a thing to maintain instead of a thing to rewrite.

**The opt-in sub-line follows the ending.** It said "Enter your details to see your results"
on the signup funnel, which has no results.

**Neutral retake-lock copy.** It used to say "Meaningful emotional and behavioural change
requires time and consistent implementation" on a B2B lead-qualification funnel. System
screen copy now lives in `features/assessment/flow/stage-defaults.ts`.

**"Email My Previous Results" tells the truth.** The server reports whether a result and a
deliverable address actually exist; the offer appears only then.

### Tenant SaaS

**Prompt isolation.** The built-in AI versions (Bridge, V2, V1) are the owner's own work and
"View assembled system prompt" printed them in full to every tenant, on two pages. They are
now listed, previewed AND resolved only for the platform and for `Tenant.unlimited`. A
customer tenant resolving a built-in id gets null, which skips the statement, the same
fail-soft path as an unconfigured provider.

**AI runs on the platform's key.** Tenants never see a key field. The model is bound PER
PLAN as data (`AppSetting.aiPlanModels`, edited at /admin/ai) with a per-tenant override
(`Tenant.aiModelOverride`). Gate has no AI (`aiReports` is off there) and a parked workspace
generates nothing. A tenant still holding its own key keeps using it, which is the owner's
internal businesses. Haiku is the default: about $0.0045 a statement, 5.7% of Signal at the
cap, 11.3% of Agency. The response cap IS the AI cap, so there is no credit system.

**Parked = locked.** A lapsed workspace signs in, sees its data behind glass, and can do
nothing until a plan is picked. Withheld on the SERVER (children are not rendered), so
there is no class to remove. Two exemptions: billing, because it ends the lock, and the data
export, because the records belong to the customer. Middleware passes the pathname in an
`x-pathname` header because a layout is not given one.

**Plan gates.** Bulk JSON/CSV import is Agency (`bulkImport`); plain-text import stays on
every tier; EXPORT is never gated. API tokens refuse at the route, not just when minting.
Both are enforced on the action as well as the screen.

**Payments, three lanes.** Platform billing uses the owner's Razorpay. A tenant uses their
own Razorpay keys, or an external gateway via lane 3: a `PaymentHandoff` row plus an
httpOnly SameSite=Lax cookie nonce, claimed at `/api/pay/return/<tenant-slug>`, with an
email fallback when the cookie is lost (the Instagram in-app browser routinely opens
payment pages in the system browser) and an optional gateway reference parameter. Two
switches, both defaulting ON: a platform master in Settings and one per tenant in the
console. Off means the funnel runs FREE, never a payment screen that then refuses.

**Lane 3 proves a browser came back from a gateway. It does not prove money moved and
cannot see a refund.** A tenant who needs proof uses their own Razorpay keys and the real
webhook. Razorpay stays the only integration.

**WhatsApp parked** (`AppSetting.wabaEnabledGlobal`, default false). Hidden from the
composer and Settings, and the SEND PATH refuses too, so a tenant with it enabled from
before stops firing messages they can no longer see. Nothing deleted. Internal tenants keep
it. Fails closed.

**Welcome email** on provisioning, template on the singleton row, edited at /admin/nurture,
off by default, testable through the same renderer a real signup uses. The support address
comes from Settings; if unset, the paragraph offering it is removed rather than rendered
half empty.

🔴 **It carries no password and never will.** A self-serve signup chose their own, and a
mailed credential is a copy of the account in every inbox it passes through. It links to
`/forgot-password`, which mints a short-lived token when asked.

**/dashboard is a router.** Super admin to /admin, anyone with a workspace to /w. The only
page left is the genuine dead end, an account with no workspace.

**Autosave in the assessment builder** (`src/components/use-autosave.tsx`). Saves on field
BLUR when the payload actually changed, green tick anchored under that field for 2.5s,
errors red for 6s. Never in create mode, one save in flight plus one queued, ignores the
blur caused by clicking Save, never calls `router.refresh()`. The Save button is untouched.

**The platform stopped calling itself Gita.** Apply Gita is a tenant.

## 2. Decisions that must not be re-litigated

- **Autosave stays BUILDER-ONLY for now.** Decided by the owner. The app-wide sweep is
  parked, not pending. Never adopt it on the respondent funnel, sign-in, sign-up,
  forgot-password or reset-password. If it is ever widened, Settings is the hard one: four
  independent save actions share one screen, so each needs its own `useAutosave` scope or
  blurring one fires another's save.
- **No second knowledge base.** The 15 answers at `/answers` already exist and are
  maintained for SEO. In-app help renders THAT content in a drawer; new task help is written
  as new KB answers so it serves both the operator and search.
- **Tenants never bring an API key.** It reads as the product being a wrapper and hands them
  an argument against the response caps, which are the real meter. Nobody in this market
  does it.
- **No long dashes**, anywhere, including chat and docs. The 26 deliberate exceptions listed
  in HANDOVER-2026-10-05 still stand (detectors and their fixtures, applied migrations).

## 4. The gates

Before every push:

```
npx next typegen && npx tsc --noEmit && npx eslint . && npm run verify:seo && npm run verify:flow
```

Plus `verify:billing` when plans or features change, and `verify:transfer` when the
assessment shape changes.

🔴 `npx next lint` is NOT the gate. `npx eslint .` is what reproduces the Railway build.
Lint also catches what tsc cannot: an unused import left behind after deleting a component
fails the build and typechecks clean.

Migrations are hand-written (no local database). `npx prisma validate` after editing the
schema; Railway runs `migrate deploy` before the app starts, so a serving container means
the migration applied.

## 5. Operating constraints

- Staging first, main only when told. A promote is `git checkout main && git merge --no-ff
  staging`, then verify `/api/version` matches the merge SHA.
- No local builds. Typecheck, lint, `prisma generate` and `next typegen` only.
- Railway builds take 230 to 265 seconds. Wait about 265 before the first poll.
- SMTP does not work on Railway. `sendEmail` already routes ZeptoMail hosts over the HTTPS
  API; do not research this again.
- Production database reads from a laptop are blocked by the permission layer. Ask the
  owner rather than working around it.
- Both non-platform tenants (Apply Gita, Cosmetic Divine Leads) are flagged `unlimited`,
  which means `parked: false`, every feature on, and immunity from every gate added here.
  That is why none of this session's work could touch the live funnels.
